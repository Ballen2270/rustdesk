# 门派闯关自动循环

pc1 上两个客户端 = 两支队伍，各自独立走同一条流程：门派使者处"领取任务" → 右侧任务面板出现"门派闯关(N/14) 挑战xx护法"（护法名不固定）→ 点该条目自动导航到护法 → "请选择要做的事"点"进入战斗" → 战斗全程游戏自动，脚本只观察 → 战斗结束任务面板出现下一个护法 → 重复；14 个护法打完面板出现"门派闯关·领取任务"，点它导航回门派使者重新领取，进入下一轮。**活动结束的判定**：一场战斗结束后，任务面板既没有下一个护法也没有领取条目，持续 `end_grace` 秒（默认 30）→ 该窗口视为结束，不再输入。战斗可能失败：面板仍是同一护法，流程自然重点一次，不算异常、不暂停。

## 开始前

统一窗口清单、队长/账号选择和跨设备启动见 [统一启动](../STARTUP.md)。优先使用生成的目标配置；不含 `window_selection` 的旧配置仍按下述方式校准。不要为窗口位置、设备或轮数变化修改活动脚本。

**每次启动第一件事：重新截图核对客户端位置（无需询问，直接做）。** 窗口位置会变，绝不沿用上一次的配置矩形——先抓每台设备全屏，确认每个配置窗口矩形内确实是游戏客户端（顶栏 活动/排行 按钮可见），不符就重新校准矩形再启动。runner 侧有同款机械守卫：识别不到游戏顶栏 UI 会停机并把全屏截图存为运行目录的 `misaligned-<device>.png`，用它重新校准。

设计、安装或校准不等于开始挑战。用户明确说开始/试跑后才运行 `--execute`。活动**每周一 21:00** 准时开启、约 40-50 分钟结束；启动建议 `--minutes 60` 兜底。启动时用户一般已组队完毕在"门派使者领取任务"弹窗处等待——**任意已识别画面均可接管**（normal / 活动面板 / 各菜单 / 任务面板 / 战斗中）；首帧落在未知画面（加载、切换瞬态）给 20 秒收敛窗口，仍未知才暂停（期间不发任何输入）。

仓库路径以当前 checkout 为准，通过 `--repo` 传入。解释器从仓库 `.mcp.json` 的 rustdesk.command 读取。先读 `_framework/` 的模块 docstring 了解引擎边界；本 skill 的事实源在 `mcp/skills/rustdesk-menpai/`，参考截图在 `images/门派闯关/`，已验证识别的真实帧（含 icon-only 战斗帧）在 `assets/frames/`。

用 RustDesk MCP 获取 pc1 两个客户端的截图与原生分辨率建配置，按 `assets/menpai.example.json`。2026-09-28 实测两窗都在 pc1（left [0,31,957,719]、right [957,322,963,722]，右窗偏下）——仅作参考，以启动当天的核对为准；若 pc1 上有 RustDesk 聊天小窗悬浮，先最小化它（它盖得住右窗任务面板区）。配置放本地运行目录，不提交；全部使用归一化坐标。

## 运行约定

- 状态机是声明式 workflow 节点（`scripts/menpai.py` 的 build_workflow）：每个节点 = 某画面下的一步动作 + 期望的确认画面 + 超时。确认靠观察，绝不盲重试；输入超时可能已送达，暂停核对。
- 导航类点击（点任务条目去护法、点领取条目回使者）走图寻路可能跨图，超时 150 秒；超时即暂停等人工核对，不补点。
- 护法名不固定、轮数不设上限（`rounds` 只是保险丝，默认 20）；一轮 = 14 个护法，完成判定靠任务面板出现领取条目（计数语义），不靠数战斗场次。接管时若没看过本链战斗，领取条目出现**不**计入已完成轮数。
- 战斗无时限，持续观察。**战斗签名**（实测）：文字工具栏 ≥3 个战斗词，或回合数+取消，或**右下角高置信"取消"**（门派闯关战斗是纯图标工具栏，OCR 只读得出取消按钮——2026-09-28 实测两张实跑帧靠此规则识别）；已确认的战斗由锚点维持。战斗切入瞬间的地图残影（活动按钮仍可读+取消在场）判为战斗而非地图，防止误点活动按钮。
- 任务面板必须保持展开。运行中不要动客户端窗口。
- 未知画面持续 20 秒记录 warning 并禁输入，继续本地观察；识别恢复自动接续。
- 每次巡检和输入复核要求新解码帧；`stale=True` 时显示 stale，禁止识别、计轮、确认点击和输入，继续只读等待。等待期间冻结 pending 的确认超时，不把没有画面当成活动结束。新帧恢复后接续，不自动关闭其他会话持有的桥。
- 每次启动带 `--viewer --viewer-port 8791`，使用观察台查看状态。
- 鼠标输入串行；脚本锁仅约束本 skill 实例（每设备一把），拦不住外部工具。禁止另一个 agent/MCP 会话同时输入同一设备。
- 用户说停止：在运行目录创建 STOP 文件，确认 state.json status 变为 stopped；必要时对本脚本 PID 发 SIGTERM，不杀 bridge。

## 排错速查（2026-09-28 实跑教训）

- **MCP 工具调用挂死不动**：交互式 MCP server 卡住时别反复重试同一个调用——直接像 runner 一样 `open_session` 起新会话，或重启 MCP。bridge 侧的自死锁/楔死问题已在 `mcp/bridge_fleet.py` 修复（stop 自死锁、action 45s 快速失败、restart_bridge 可强杀无响应外部桥、孤儿桥闲时自动回收），但旧会话里的 server 进程要重启才带上修复。
- **某窗口一直 unknown**：先看 `recognition-<window>.json` 的 items，再核对窗口矩形是否漂移（布局每周可能变）。
- **首帧就 paused**：20 秒收敛窗口后仍未知才算坏接管；看 latest-*.png 实际画面。
