# 双客户端抓鬼

用户先在 pc1 组好两队并展示两个队长客户端。默认每个窗口本次完成 **5 轮单倍**，两窗独立计轮、串行输入。用户指定窗口、轮数或双倍模式时按其要求执行。

脚本 [scripts/zhuagui.py](scripts/zhuagui.py) 使用本机 Apple Vision OCR 与 Pillow 战斗图像锚点识别，通过 RustDesk MCP 点击/滚动并持续观察。运行循环不调用在线模型。模型负责校准、启动、读取进度和核对异常，不能替代脚本承担逐帧轮询。

## 开始前

统一窗口清单、队长/账号选择和跨设备启动见 [统一启动](../STARTUP.md)。优先使用生成的目标配置；不含 `window_selection` 的旧配置仍按下述方式校准。不要为窗口位置、设备或轮数变化修改活动脚本。

制作、安装和校准不等于实战。用户明确要求开始/试跑后才运行 `--execute`；未授权时可离线回放或只读 observe。

先读 [运行说明](references/operation.md)，查看 [图片流程](references/flow.md) 以辨认 1–9.png。脚本事实源在仓库 `mcp/skills/rustdesk-zhuagui/`，个人技能目录是链接；基础模块复用同仓库 `_framework`。

每次启动脚本先对每个设备截全屏并**自动重新定位窗口**（顶栏锚点优先，标题栏像素兜底；配置 `rect` 只是尺寸提示，`autocal:false` 仅 mock 用），再核对队长身份。填写 [配置示例](assets/pc1.example.json) 提供尺寸/身份后设 `calibrated=true`。pc1 可能有多个显示设备，确认实际设备名；任何设备同理。配置和运行记录放本地临时目录，不提交账号数据。

先 inspect/observe 核对当前识别，再按用户已授权的目标运行。执行模式从任意画面开始：中途遇到的已领取战斗/任务会被收编（轮末弹窗仍是有效完成证据）；漏看轮末（弹窗被遮挡或被倒计时取消）不计数、按 40 点记账后自动重新领取，不冻结等人工。

## 图片顺序与循环

1. 分别打开顶部“活动”，在“日常活动”列表上下滚动找“捉鬼任务”，点击同一条目对应的“参加”（1.png）。同名参加按钮必须属于同一行、同一列，不能点到其他活动。
2. 等待自动导航到钟馗菜单（2.png），点击右侧菜单首项“捉鬼任务”，确认右侧出现“捉鬼(1/10)”（3.png）。
3. 领取后小概率弹出「双倍点数不足」确认框：识别到居中弹窗含"双倍/不足"字样即点其左下"取消"（`POPUP`/`POPUP_CANCEL` 区域为暂定几何，待实拍图校准；按钮漏读时软重试不暂停），流程随即恢复。
3. 领取确认后先在场景空白安全点点一下关闭钟馗残留对话（对话开着时点任务面板不触发寻路），再观察是否已经自动移动；原地停留时点击右侧捉鬼任务区域启动导航。新鲜截图持续证实同一任务、同一坐标原地不动时，才允许补点一次；仍不动或点击超时则暂停核对。
4. 等待自动导航（4.png）和游戏自动战斗（5.png），通常 10 场，偶尔追加第 11 场“千年厉鬼”，都等待结束。顶部数字是本场战斗回合，不是抓鬼场数。
5. 看到“少侠已经捉完1轮鬼，是否继续捉鬼？”（6.png），且本次已领取并观察到战斗，去重计一轮。未达目标时，每窗口每轮独立随机等待 **10–40 秒**，到时重新截图确认弹窗仍在，再点击“确定”，自动回长安钟馗菜单（7.png），再次点击“捉鬼任务”。8.png、9.png 是再次领取后的任务面板，按 3 处理，底部 NPC 对话残留不影响任务已领取的事实。
6. 达到该窗口目标后立即停止后续输入，不再续领；最后弹窗留给游戏倒计时或用户处理。另一队继续完成自己的目标。

“一轮”是完整一组抓鬼，包含可能的千年厉鬼。只以轮末提示确认，不能数十次战斗或读取任务的 10/10 就补记一轮；同一弹窗多帧只计一次，弹窗里的“1轮”不是累计轮数。

## 双倍点数

只有用户明确要求双倍才规划双倍。按用户约定，每完整一轮预算 **40 点**，包含可能的第 11 场，不额外加点。每账号分别计算 `floor(P / 40)` 完整轮，余数留存；200 点是 5 轮，180 点是 4 轮、剩 20 点。一个点数归属不明时先澄清，可继续只读观察；不能在两队间共享或复制余额。

双倍窗口配置 `mode="double"`、该账号的 `double_points`。省略 `rounds` 才按点数推导；明确轮数或 `--rounds` 不得超预算。点数不足 40 不开新轮，双倍结束不自动补单倍。混合任务分别设置各窗口计划。

九张图未展示模式开关。用户先配置游戏内单/双倍；双倍开始前核对实际模式和点数后设置 `reward_mode_confirmed=true`。脚本不猜开关路径、不领点数或购买点数。`estimated_spent` 是按轮数计算的预算，不是假称实时读取游戏余额。

## 运行与停止

- 操作前后帧长期保留；巡检帧只覆盖 `latest-*.png`，不保存状态变化图片历史，运行结束或暂停后清理其他 PNG，保留日志和前后帧。
- 使用本地长任务脚本，通过 `state.json`、`events.jsonl`、`latest-*.png` 和 `recognition-*.json` 看进度/异常，保留终端 session_id。脚本每分钟续约 MCP 租约。
- 两窗交替巡检，战斗无固定时长上限；轮末等待使用截止时间，不阻塞另一窗操作和 STOP。随机时长每轮只抽取一次，不因重复截图或短暂未知状态重新计时。未知状态二十秒后 warning 并禁输入，识别恢复可接续；掉线、矩形变化、任务丢失和未决点击暂停相应窗口。
- 点击落点在目标内随机偏移，先调用 MCP `mouse_move` 多步拟人移动，再复核目标并点击；滚轮采用随机分段、间隔和漂移锚点。每次输入前重新截图，意图与 pending 先落盘；超时可能已送达，不盲重试。漏轮末直接回菜单不猜数。战斗锚点只维持已确认战斗，不能触发操作或计轮。
- 同一 pc1 不同时执行其他自动活动或手动 MCP 输入。脚本兼容现有活动锁，但不能阻止外部操作者移动鼠标。
- 用户说停止，创建运行目录 `STOP`，确认 status 为 stopped；必要时只终止本脚本，不杀 bridge，不退出游戏，不中断已经开始的自动战斗。在途输入不能撤销。
- 不自动从旧记录重启。先核对已完成数和 pending；确认无未决轮次后按各窗口剩余目标/点数建立新运行目录。

## 验证范围

运行前查看 [离线验证结果](references/validation.md)。测试包括纯逻辑、九图实际识别回放、mock MCP 双窗口完整循环及 observe/STOP。没有真实 pc1 试跑；千年厉鬼只验证等待语义，未提供其真实截图。陌生异常弹窗和双倍界面不宣称已识别验证。首次实战按用户授权先校准、observe、试一轮。

运行器默认开启逐窗口区域 OCR 缓存：仅在新截图的区域像素、尺寸、坐标与放大倍数完全一致时复用识别结果。点击前的新帧和移动后复核照常执行。配置 `ocr_cache: false` 可恢复原 OCR 管线；缓存只保留在本次运行内，不写入账号配置或证据图。离线耗时与限制见 [启动验证](../STARTUP-VALIDATION.md)。
